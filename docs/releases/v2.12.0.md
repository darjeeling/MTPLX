# MTPLX 2.12.0

This release adds two models and makes Flash-Next faster on long prompts. Ternary Bonsai 2 27B from Prism ML is an 8.85 GB model with image input and a draft head, and it runs on Macs with 16 GB of memory. Flash-Next Optimized Quality is an 8-bit build of Qwen 3.8 Flash-Next for Macs with 256 GB or more. On the same Mac and the same prompts as 2.11.3, Flash-Next reads a 65,502-token prompt 42 percent faster, shows its first token after 60.1 s instead of 85.5 s, and decodes it 13 percent faster. On a 4,061-token prompt the first token arrives after 2.88 s instead of 5.26 s. Image requests now use the compiled verifier on Flash-Next and on the dense 27B. The release also fixes thinking that leaked into the answer when a prompt quoted tool markup, Gemma 4 replies that failed after they were generated, conversations that were processed again after Stop, long sessions that lost their saved state, a memory guard that could not see memory held outside the GPU allocator, and a repetition stop that cut code that repeats exactly, such as a game board; the stop is now off by default. On Macs with 160 GB or more the n-gram table now streams from SSD, which leaves about 30 GB more memory for context and the session cache.

Measured on an M5 Max with 128 GB, 2.11.3 against 2.12.0 on the same Mac and the same Python runtime, alternating boots (2.11.3, 2.12.0, 2.12.0, 2.11.3), one model loaded at a time, fans at maximum, the GPU memory limit raised to 120 GiB (`iogpu.wired_limit_mb=122880`; the default is about 96 GiB), at the model's own sampler settings with seed 1731, thinking off, 512-token answers:

| | 2.11.3 | 2.12.0 |
|---|---:|---:|
| Flash-Next time to the first token, 65,502-token prompt | 85.5 s | 60.1 s |
| Flash-Next prompt processing, 65,502-token prompt | 768 tok/s | 1,094 tok/s (+42%) |
| Flash-Next decode, 65,502-token prompt | 56.1 tok/s | 63.5 tok/s (+13%) |

| Flash-Next decode, 4,061-token prompt | 74.4 tok/s | 74.1 tok/s (tie) |

## Speed

### Flash-Next on long prompts

- **Attention memory is no longer copied on every verify round.** MLX writes into an array in place only when its buffer is at most 16,384 bytes larger than the array, and its buffer cache can hand back a buffer up to 32,768 bytes larger than asked. The attention banks were sized on a 4-row step inside a 256-row buffer, so at many prompt lengths the first write landed in a recycled buffer that could never be written in place again, and all 24 key and value banks (135 MB each at 128K) were copied on every verify round. The banks are now sized on the cache's own growth step. The 24 writes went from 7.8 ms to 0.6 ms, and the twelve attention layers of the verify from 30.9 ms to 11.2 ms at 131K tokens, with bit-identical output. The 65,502-token prompt in the table above is one of the lengths that triggered this copy on 2.11.3.

### Flash-Next prompt processing

On M5 chips, Flash-Next reads prompts in 4,096-token chunks and switches to sparse attention from 16K tokens for those wide chunks. Other chips keep 2,048-token chunks and the 32K switch point. The kernels behind the chunks were rebuilt at the same time:

| Change | Before | After | What was measured |
|---|---:|---:|---|
| Sparse prompt attention reads the cache in place, same bits | 19.8 µs per row | 7.1 µs per row | the kernel alone at 64K |
| Block selection on one simdgroup per row, same selections | 2.68 µs per row | 0.58 µs per row | score and select at 18K |
| The same, at 64K | 3.57 µs per row | 2.51 µs per row | score and select at 64K |
| The hyper-connection write as one fused kernel, same bits | 0.22 µs per token | 0.14 µs per token | one write at 4,096 rows |
| A new GPU program for every new context size | 40 to 56 ms per size | none | block selection |
| The last chunk of a cold prompt cut into 256-row forwards | 842 tok/s per forward | 1,763 tok/s at 2,048 rows | per-forward prefill speed |
| Memory still allocated between prompt chunks | 88.86 GB | 85.84 GB | Flash-Next, 4,096-token chunks |

- **The n-gram table is read in a better order.** A cold prompt's first chunk spent 0.65 s gathering n-gram rows, 20 percent of a 4K cold prefill, because the pre-read filled a slice of the 23.8 GiB weight file and none of the two 3.0 GiB scale and bias files. The pre-read now fills the small files first, and the warm pass before a large gather reads only the files that are not already in memory, a third of the system calls.

- **A warm agent turn reprocesses at most 64 tokens at the end of its prompt instead of up to 256.** The saved restore point nearest to the end of a prompt now sits 64 tokens before it.

- **Restore points are recorded inside the last wide forward.** Every Flash-Next forward of 64 rows or more reads nearly all 512 experts of every layer, and the restore points used to end two extra forwards behind every cold prompt and one behind every warm agent turn. They are now recorded inside the last wide forward, at the same positions. On the same build, a cold 4,061-token prompt prefills in 2.79 to 2.81 s instead of 3.06 to 3.10 s, alternating the setting off, on, on and off. `MTPLX_GDN_BOUNDARY_INFORWARD=0` restores the old layout.

### Flash-Next decode

- **All sampled draft depths are built with one device sync.** The device predicts the host's draw, the host checks every pick with the same arithmetic as before, and a pick that does not match ends the chain and finishes the round the old way, so the tokens are identical for every seed. Draft preparation at 4K went from about 5.2 ms to about 4.4 ms per round.

- **Draft depths go to the GPU as they are built,** and the n-gram rows of the verify window are read while the GPU works. A later comparison at equal GPU clocks was flat, so no speed gain is claimed for this change on its own.

The 27B is unchanged in this release. Measured the same way as the headline table, with the Optimized Speed pack:

| 4,061 tokens | time to the first token | 6.07 s | 6.07 s |
| | prompt processing | 680 tok/s | 679 tok/s |
| | decode | 46.7 tok/s | 44.2 tok/s |
| 16,350 tokens | time to the first token | 26.7 s | 27.2 s |

## New models

### Ternary Bonsai 2 27B (issue #515)

MTPLX runs Prism ML's Ternary Bonsai 2 27B, a 2-bit ternary model built from Qwen3.8-27B, with image input. The pack `Youssofal/Ternary-Bonsai-2-27B-MTPLX-Optimized-Speed` carries Prism ML's language model and vision tower byte for byte (8.60 GB) and adds the Qwen3.8-27B draft head (0.24 GB), 8.85 GB in total. The served id is `mtplx-bonsai-2-27b-optimized-speed`. MTPLX applies Prism ML's Hadamard rotation at run time and refuses a pack whose rotation metadata or vision tower is missing. Full credit for the model goes to Prism ML, and the pack carries their license and notice.

The draft head is on by default at depth 1. Two GPU kernels written for this pack make every Bonsai round cheaper:
- The Hadamard rotation runs as one kernel. It returns the same bits as the four operations it replaces.
- A ternary kernel serves the verify and decode rows of the 2-bit projections. It is as close to Prism ML's own float32 reference as the stock kernel: mean KL 2.92e-6 against 3.02e-6 over 1,630 positions from code, prose and reasoning. Greedy output is identical with the kernels on and off.

The verify step also runs compiled on Bonsai now, with 0 divergent rounds in 613 compiled rounds checked against eager verification.

Measured on the same M5 Max, alternating boots of 2.12.0 without these kernels and with them, one model loaded at a time, at temperature 1.0, top-p 0.95 and top-k 20, thinking off, 512 generated tokens. The 27B ran in the same session:

| Prompt | Bonsai before the kernels | Bonsai, 2.12.0 | Qwen 3.8 27B Optimized Speed, 2.12.0 | Peak memory, Bonsai and 27B |
|---|---:|---:|---:|---:|
| 4,061 tokens | 50.4 tok/s | 64.4 tok/s (+28%) | 52.6 tok/s | 11.4 and 23.9 GB |
| 16,350 tokens | 45.2 tok/s | 57.1 tok/s (+26%) | 51.0 tok/s | 14.6 and 27.0 GB |

Bonsai is now faster than the 4-bit 27B at both lengths, in half the memory, and it reads prompts 7 to 8 percent faster than before. With the new kernels, depth 3 measured 14 percent slower than depth 1 over a 3,000-token answer, so depth 1 stays the default. The draft head comes from Qwen3.8-27B and accepts 75 percent of its drafts on Bonsai.

- **Medium reasoning by default.** Bonsai supports two reasoning efforts, `medium` and `xhigh`, and `medium` is the default in the app, the CLI and every connected client. Prism ML states that `low` is not supported. On a stopwatch coding task, `xhigh` spent 577 s and 21,848 reasoning tokens without reaching an answer, while `medium` finished the task and a correction turn.

- **16 GB Macs.** A tight Mac could not run Bonsai before this release, because the memory planner refused any model whose budget could not also fund the 1 GiB session cache floor. That floor limits the warm cache and is not a physical need. When it is the only thing left unfunded, the planner now admits the model with the cache floor at zero, and restores come from the SSD. This applies to packs whose weights are no larger than the Bonsai pack's 8.83 GB, the pack the margin was measured on; Qwen 3.5 9B Optimized Speed, for example, gets a 20,480-token window on a 16 GB Mac. A larger pack is admitted this way only when it carries its own measured memory table. A pack that could fund the floor keeps it, unless dropping it would give a larger window, so a lighter pack never gets less context than a heavier one; no catalog model's window changes.

- **Memory by Mac size.** Measured by limiting a 128 GB M5 Max to each class's memory budget, with text prompts, and with the draft head and the vision tower loaded:

| Mac memory | Engine budget | Context window | Peak, prompts up to 8K | Peak, 16K prompt |
|---|---:|---|---:|---:|
| 16 GB | 12.0 GiB | 8,192 tokens, no warm cache in RAM | 11.55 to 11.80 GiB | 12.11 GiB, over the budget |
| 18 GB | 13.5 GiB | 20,480 tokens (36,864 with 8-bit KV) | 11.55 to 11.78 GiB | 12.28 GiB |
| 24 GB | 18.0 GiB | 94,208 tokens (167,936 with 8-bit KV) | 11.55 to 11.78 GiB | 12.28 GiB |

With the draft head active under the 16 GB budget, a 7,006-token prompt and a 1,024-token answer peaked at 11.54 GiB of GPU memory and 12.79 GiB for the whole process, with no swap growth. The peak sits about 3.1 GiB above the weights and the KV cache in every run, which is what the planner reserves.

### Flash-Next Optimized Quality

An 8-bit build of Qwen 3.8 Flash-Next: the main model and the draft head at 8 bits with group size 64, the structural weights in BF16, and the n-gram table at 4 bits with group size 32. The download is 169.96 GB (169,958,537,520 bytes in 57 files) at `Youssofal/Qwen3.8-Flash-Next-MTPLX-Optimized-Quality`, and the weights need about 128.5 GiB of memory with the n-gram table on SSD. All 2,860 of its tensors were checked, and sampled values in 25 groups were compared with the BF16 source. Forge builds it with the `flash-next-optimized-quality` recipe, and one command builds it, loads it and tests chat, a tool call and an image:

```bash
bash scripts/build_flash_next_quality_pack.sh Qwen/Qwen3.8-Flash-Next <output directory>
```

The pack has not yet been run on a 256 GB Mac, so on those Macs the app and the CLI recommend Flash-Next Optimized Speed first and list Optimized Quality second. Its speed has not been measured.

Forge also converts Flash-Next source models directly (PR #508, Bradford Matthews). It used to stop with `Model type qwen4_exp not supported`. The 51B n-gram table is quantized one shard at a time straight into its own file, and the trunk is converted one tensor at a time with MTPLX's own model code.

## Recommendations and memory

The app and the CLI read one catalog of 25 models with the same names, sizes and recommendation rule, and model descriptions follow the app language in all 13 languages without a restart. The first recommendation on M3, M4 and M5:

| Mac memory | First recommendation | Flash-Next options |
|---|---|---|
| Below 16 GB | Qwen 3.5 4B Optimized Speed | none |
| 16 to 31 GB | Ternary Bonsai 2 27B | none |
| 32 to 95 GB | Qwen 3.8 27B Optimized Speed | none |
| 96 to 255 GB | Qwen 3.8 27B Optimized Speed | Bare Speed from 96 GB, Optimized Speed from 128 GB, Optimized Quality from 192 GB |
| 256 GB and above | Flash-Next Optimized Speed | Optimized Quality second |

M1 and M2 keep their FP16 recommendations, and an existing selection is kept.

- **The n-gram table streams from SSD on every Mac.** On Macs with 160 GB or more, earlier releases also loaded the 29.8 GiB table into GPU memory, and nothing in 2.12.0 reads that copy. It now streams from SSD on every Mac and is never wired. On 256 GB and 512 GB Macs this raises Flash-Next Optimized Quality's memory for context and the session cache from 29.7 to 59.5 GiB, and lowers the memory it keeps wired from 164.3 to 134.5 GiB.

- **The GPU wired limit is clamped to what the Mac allows.** When the memory the engine wanted to keep wired was above the limit macOS allows, MLX refused the request, the error was dropped, and the model ran with none of its memory wired and no GPU keepalive. That meant extra time after every idle pause and memory that macOS could evict under pressure. The wired limit is now set to the largest value the Mac accepts, so most of the model stays wired and the keepalive runs. The startup log says how much macOS allowed and gives the `sudo sysctl iogpu.wired_limit_mb` command that wires all of it. On a stock 96 GB Mac that limit is about 72 GiB.

- **96 GB Macs are pointed to Flash-Next Bare Speed.** Optimized Speed peaks at 87 GiB and Bare Speed at 78 GiB. On 96 GB, Flash-Next has one 84 GiB engine budget, shared by the catalog, the memory planner and the verify memory check, with a planned window of 86,016 tokens on M5 (20,480 tokens on chips without tensor units).

- **A model that does not fit gets the smallest window instead of the largest.** A plan whose verdict was "does not fit" was turned into "no limit", so the 27B picked by hand on a 16 or 24 GB Mac, and Flash-Next on 96 GB, were served the full 262,144-token maximum under a MODEL DOES NOT FIT banner. They now get the 4,096-token floor window and one startup line that says so. An explicit `--context-window` still wins, and a Mac that fits resolves as before (the 27B: 57,344 tokens on 36 GB, 204,800 on 48 GB, 262,144 from 64 GB).

- **The decode context ceiling follows the model.** Every model was budgeted with the 27B's 65,536 KV bytes per token (Flash-Next uses 24,576), and every Flash-Next start printed a warning about it. The value now comes from the model's config. On 16 and 24 GB Macs the 27B ceiling is 65,536 and 98,304 tokens instead of a flat 131,072, and no default on 32 GB or more moves.

- **The SSD session cache size follows RAM from the terminal too.** `mtplx serve` defaulted to a flat 100 GB, so a 16 GB Mac got a 100 GB store while the app scaled it. The default is now the same everywhere: 16 GiB on Macs with 16 GB of RAM or less, 24 GiB up to 32 GB, 32 GiB up to 64 GB (100 GiB when the disk has at least 150 GiB free), and 100 GiB above 64 GB. An explicit size still wins.

- **The memory guards account for the rest of the Mac (#516, PR #500 by Maikel Vos).** A 128 GB M5 Max serving a long OpenCode session with `allow_swap` on was restarted by the kernel watchdog with the MTPLX worker at 118 GiB resident, while the engine's guard read below its warning level the whole time, because it measured only what the GPU allocator held. The guards now read the process footprint the kernel's memory manager uses, so memory outside the allocator counts, and they read the kernel's own figure for the memory it can still hand out (the number behind `memory_pressure -Q`). A large prompt is admitted only when both the engine and the rest of the Mac have room for it. The abort floor is 2.5 percent of RAM (3.2 GiB on a 128 GB Mac, never under 1 GiB) and the shed floor is twice that. Under the shed floor the check runs every 2 s instead of 10, so a request under sustained pressure is stopped about 6 s after the floor is crossed instead of 30. `allow_swap` still admits a prompt past the machine's fit, but it does not turn this guard off. `MTPLX_SYSTEM_MEMORY_GUARD=0` turns it off, and `MTPLX_HOST_MEMORY_ALLOWANCE_BYTES` sets how much memory a daemon may hold outside the GPU allocator before it counts.

## Images

- **Flash-Next image positions are consistent through the whole reply.** Since 2.10.1 only the main verify forward used the image positions. The copy rounds, the repairs and the final save of a reply used plain text positions, so after a 1,024-token image those rows sat about 990 positions from where they belonged, in RAM and in the SSD copy. All eight forward sites now use the image positions. Saved Flash-Next image conversations carry a new cache key, so an existing image conversation is processed again from its first image once after the update; the text before that image is still reused.

- **Flash-Next image requests use the compiled verifier.** An image request used to fall back to eager verification for the whole conversation. The image position offset is now an input of the compiled step, so requests with different images share one compiled program and text requests are unchanged. A 2,439-token image prompt decoded at 101.6 tok/s compiled against 97.2 eager, with the same answer. That answer was 81 tokens long, 22 verify rounds. Per round the compiled route costs 4.5 percent less than the eager one and 2.3 percent more than a text request on the same boot. An OpenCode image task through the app ran 678 of 678 verify calls compiled at 77.1 tok/s. Image turns now use the same compiled verifier as text, and on 440 image rounds it agrees with the slower eager route as closely as it does on text. Six prompt shapes the compiled step cannot represent stay on the eager route, and `MTPLX_QWEN4_VISION_COMPILED_VERIFY=0` turns the route off.

- **Dense 27B image requests use the compiled verifier too.** Eighteen complete requests, half with thinking on, compared 762 compiled image rounds and 511 text rounds against the eager verifier from the same cache, with zero differences in logits, hidden states and cache state. `MTPLX_DENSE_VISION_COMPILED_VERIFY=0` keeps dense image requests on the eager verifier.

- **Qwen 3.5 and 3.8 27B, and Bonsai, place image tokens at their grid positions,** the position scheme the models were trained with. The small-tensor reference agreed within 0.000005.

- **Adding an image reuses the conversation before it.** A Pi conversation processed 154,899 tokens again, 184 s, after an image was attached. Image requests now restore the saved text history like text requests do, and the image contents are checked before any history that depends on an image is reused.

- **Image placeholder text stays text (PR #519, François-David Collin).** A client that sent the image placeholder string back as plain text, for example an earlier turn's result saved as text, made the chat template render it as a real image slot, and the request was refused with "prompt contains more image placeholders than images". Only real image parts create image slots now. Placeholder text is kept as readable, escaped text in message content, in reasoning and in tool-call arguments, so an agent that edits code containing a placeholder keeps its image turns.

## Fixes

- **The repetition stops are off by default.** In 2.11.3 and earlier, the server ended a reply when a block of up to 96 tokens repeated four times in a row, and deleted every copy. Exact repetition does not prove a loop, because code repeats exactly. The stop cut a Tetris board literal at its ninth identical row, an empty sudoku grid, a 256-entry table of zeros and 64 identical board `<div>` lines, and it cut a correct patch that renamed a type at 15 identical call sites partway through, so the tool call never closed. Replaying the stop over 301,194 saved replies on the test Mac (104.6 million tokens from the MTPLX app, OpenCode, Hermes, Pi and Codex) found two real patches it would have cut. Nothing in the engine now ends a reply because text repeats: a reply ends at the model's own stop, at the request's token limit, or at Stop.

- **`MTPLX_REPETITION_STOP=1` turns the stop back on,** together with a new check for exact loops with a period of 97 to 8,192 tokens. That check ends a loop once three whole copies are in, never before token 768, at 0.4 to 1.5 microseconds per step. With it on, a 4-bit test build of a 9B model that repeated a 129-token block 94 times stops at 5,202 tokens instead of 16,916, and `/health` and the request log give the reason `long_cycle`. The new check can also cut legitimate code: it ends a platformer map with 8 identical empty rows of 60 tiles.

- **Quoted tool markup no longer ends the thinking.** Pasting a traceback that contained `</parameter>` made the rest of the model's thinking appear in the visible answer, starting at the tag. A thinking block now ends only at `</think>` or at the start of a real tool call: tools must be declared for the request, the call must start a line outside a code fence, and a bare `<function=NAME>` must name a declared tool. The same rule decides whether an answer that was only thinking is retried, and a retry that is fed a tool result starts its stream clean. 10 streamed requests with the 27B that quote up to 43 tool tags inside one thinking block all kept their thinking in the reasoning pane, and the rule has 117 cases in its test.

- **A made-up tool call in a reply without tools is hidden completely.** The stream filter closed its hidden span at the first `</function>`, so the block's own `</tool_call>` reached the user as visible text. It now waits for the closing tag that matches the opening one.

- **Gemma 4 streamed replies finish again (#517).** A reply without tools generated normally and then failed with `'Gemma4ThinkingContentStreamSplitter' object has no attribute 'suppressed_tool_markup_chars'`. Every stream splitter now provides the fields the stream reads. A streamed reply finished with `stop` after 418 frames, with the reasoning separate from the answer, and the splitter test went from 12 failures in 37 cases to 37 passing.

- **Stop, then send again, keeps the conversation.** After Stop the app changed the conversation's session id, so the next message reached the daemon as a new conversation and processed the whole prompt again (26,294 tokens and 24.5 s to the first token in the report). The app now keeps the session across a Stop, and the daemon lets the next request wait, for at most 30 s (`MTPLX_SESSION_CANCEL_HANDOFF_WAIT_S`), while the stopped generation lets go of the session, instead of refusing it with a 409. A retry 1.975 s after Stop reused 10,918 of 10,928 prompt tokens, and a complete retry reused 6,144 of 6,225 and finished a 9,555-token answer.

- **Long sessions keep what they need to resume (#499).** When a conversation was larger than its RAM cache allowance, the cache kept a reference to the live state instead of a copy, and that entry dropped the draft head's history. The next turn could not restore, the SSD copy was refused for the same reason, and the whole prompt was processed again: 570 s to the first token for a 149,649-token prompt in the report, on every turn. The history is now kept in RAM and in the SSD copy (about 4 KB per token, next to 64 KB per token of model state). An SSD copy saved by an earlier release without it is processed once more after the update.

- **Old conversation states are counted and released (#456, diagnosed by peterloron).** Those same reference entries recorded 0 bytes, so every memory check missed them, and a turn that could not reuse one built a new cache and left the old one allocated: memory grew by 3.7 GiB per turn on a 64 GB M4 Max. The entries now report what they hold, a session keeps at most one, and eviction and `/admin/cache/clear` release the memory they point at. `/health` shows `lease_entries` and `lease_nbytes`.

- **Saving a session to SSD gives way to a waiting request (#505, reported by peterloron).** On a 64 GB Mac with the 27B at about 104K tokens, the SSD save held the model for more than 500 s while a request waited, and the stream watchdog ended that request at 300 s. Each piece of the save is now at most 32 MiB, with a check for waiting work after each one. A deliberately slowed test interrupts the save in under 200 ms, and the files on disk are byte for byte the same. `/health` reports `encode_units`, `encode_slow_units` and `encode_longest_unit_s`.

- **Tool conversations keep their prompt history.** With thinking off, the prompt cut the empty thinking block in two, so from the second request of a tool session the history no longer matched the saved state. An audit of 2,020 conversation turns found the unexplained differences from the model's own chat template fall from 848 to 0, and the predicted reusable history matched the next request in 834 of 834 cases, up from 498. For OpenCode with thinking on, turns that extend the saved stream went from 28 of 36 to 36 of 36.

- **A stuck request can no longer hold the fans at maximum (PR #295, Patronum).** In Smart fan mode, one report had both fans at maximum for about 15 hours behind a request whose client had gone. A request now counts as activity only while the model makes progress. After 180 s without progress (`MTPLX_FOREGROUND_STALL_DEADLINE_S`) it stops counting, and the fans return to automatic 120 s later. Batched prompt processing now reports its progress too, so a healthy long prompt no longer trips the 300 s stream timeout.

- **Plain decoding has one path (PR #507, David Tai).** David Tai found that the optional pipelined plain decoder drew its first token from a different random stream than every later token, so one seed gave different text depending on the path, and his change made the two agree. After this release's n-gram change no model offers the pipelined mode, so the path and its `MTPLX_AR_PIPELINE` switch are removed and plain decoding always runs the classic loop.

- **Draft heads imported from a raw checkpoint accept again (PR #511, Stuart Rowlands).** Hugging Face checkpoints store the draft head's norm gains centred on zero, and only Forge restored the +1.0 convention. A head added any other way loaded without an error and then accepted about 0 percent of its drafts (the right token landed at a median rank of 247,513 of 248,320). The loader now applies the same correction Forge does, and a head that is already correct passes through byte for byte.

- **Eager BF16 verification uses the same attention-gate rounding as compiled verification.** This covers the gated attention of the BF16 Qwen3-Next, Qwen 3.5, 3.6 and 3.8 models when verification runs eagerly: image requests, contexts past the compiled route's 32,768 tokens, buffer-growth fallbacks, warm-restore rounds and single eager forwards inside a compiled request. The compiled verify, prompt processing and plain decoding are unchanged, and so are the Float16 and Float32 attention gates, Bonsai, Gemma 4 and Flash-Next.

- **Downloads behind a company proxy explain the certificate error (#495).** A `CERTIFICATE_VERIFY_FAILED` error now names the TLS-inspecting proxy as the cause and lists both fixes (`SSL_CERT_FILE`, or the `truststore` package). With `truststore` installed, downloads verify through the macOS keychain; `MTPLX_SYSTEM_TRUST=0` turns that off.

- **Forge builds a model that ships as one weights file (#492).** A single `model.safetensors` has no index file, so Forge found no draft head, wrote no `mtp.safetensors`, and stopped with `return_hidden requires an MTP-patched runtime`. Forge now reads the file headers, as `mtplx inspect` does.

- **A Qwen model with MiMo in its name keeps the Qwen settings.** Xiaomi also ships Qwen-architecture distills named MiMo, such as MiMo-V2.6-Distill-Qwen-9B. MTPLX picked the model family from the folder name, so these were served with the MiMo settings: draft depth 1 only and reasoning off. The family now comes from the checkpoint's own architecture, so such a distill keeps the Qwen 3.5 settings, depths 1 to 3 and reasoning on.

- **The packed-GQA verify counter counts accepted windows too (#506).** It counted only the windows it declined, and only while the compiled verifier was being traced, so a healthy daemon showed 96 declines and no accepts. `/health` now counts both.

## The app

- **Cancelling a start no longer crashes the app.** The crash read "freed pointer was not the last allocation". Two default arguments of the daemon supervisor were asynchronous closures, and copies compiled into different modules disagreed on their frame size. They are named functions now. The reproduced case went from 3 failures in 3 runs to 3 passes, and a start cancelled with Stop no longer writes a failed-start report.

- **A failed start leaves a log that `mtplx doctor` can show (#504).** The app used to show one cut-off line. It now writes the server's last output to `~/.mtplx/logs/last-failed-start.log`, with secrets masked, and `mtplx doctor` includes the last 60 lines while the file is less than 14 days old.

- **The open inference menu no longer loads the CPU.** Live metrics redrew the whole app scene, including the open menu. With the menu open during inference, the app's CPU use went from 47.9 and 27.4 percent to 2.2 and 3.3 percent, and Bonsai decoded 48.5 tok/s in both runs instead of 45.5 and 46.9.

- **Activity and Cache show every saved prefix.** Several prefixes saved from one conversation shared one row identity, which hid entries the engine still held (19 prefixes across two sessions in the report). Rows are now keyed by the session and the token hash.

- **Setup uses the runtime and model defaults it selected.** An app runtime started from another MTPLX folder could import that folder's Python package first, report the wrong version and fail setup. When tuning is skipped, the installed pack's own depth now applies, so Bonsai starts at depth 1 instead of the general default of 2.

- **Downloaded models can be removed from the app (PR #377, Philip John Basile).** Removal asks for confirmation, removes exactly the folder shown, refuses the model being served and says why when it refuses. Additional model folders stay read-only, and the controls are in all 13 languages. `mtplx remove` now treats a folder name you type exactly as that folder, even when it matches a public alias, and a typed `--cache-dir` selects that folder.

- **Long model names stay readable in the model list.** A name that does not fit is now shortened in the middle instead of at the end, so the part that tells two builds of a model apart, such as 6-bit or a folder suffix, stays visible. Resting the pointer on a name in the list, or on the model name in the top bar, shows it in full.

- **Every model folder keeps its own name and row in the model list.** When a pack declared no name of its own, the list named its folder after the model it was built from. Two builds of one source, such as a 4-bit and a 6-bit, shared one row named after that source, and the row launched whichever build was found first. A downloaded Qwen 3.8 27B Optimized Speed was also listed a second time as Qwen3.8-27B, because the pack records the model it was built from. Under the old rule, seven folders on the test Mac took the name Qwen3.5-4B. A folder now shows the name its pack declares, or else its folder name, and each folder has its own row.

- **The free-disk check before a download matches the download.** The app asked for 2.5 times a model's download size in free disk, about 396 GiB for Flash-Next Optimized Quality. It now asks for the bytes still to download plus 5 GiB, the same rule `mtplx pull` uses.

- **Use MTPLX settings for connected apps.** A switch in the inference settings decides whether MTPLX or the connected client controls the request settings. It is on by default, and the native per-chat controls work either way. Pi follows the live reasoning setting and restores its own choice when the switch is off. A settings read that took about 1 s now takes 2 to 10 ms.

- **One launch setup for the app, `mtplx start` and `mtplx serve`.** The same client on the same model used to get different engine settings depending on how the daemon was started. Pi now runs on the serial scheduler from every entry point (the OpenCode preset measured it at 51.4 against 36.8 decode tok/s at 8K), the SSD cache size is automatic everywhere, the minimum saved prefix is 512 tokens everywhere, and the app's presets no longer fix the prompt chunk at 2,048 tokens for every model. A test builds the app's launch command for 294 combinations of client, model family and Mac size and compares it with the engine's own table.

- **The inference panel no longer pins a 2,048-token prompt chunk.** When nothing was saved, the panel showed 2,048 and sent it with every settings change, such as a temperature or depth change. The app then saved it, and every later launch passed `--prefill-chunk-tokens 2048`, which overrides Flash-Next's own 4,096-token chunk on M5. The release gate's copy of a real app launch carried exactly that setting, and a cold 40K prompt read about 978 tok/s there against about 1,400 without it. The panel now sends a chunk only when you choose one, an Auto option hands the choice back to the engine, and a 2,048 saved by an earlier build returns to the engine's choice once.

## Server, CLI and Forge

- **Performance reports explain a slow response.** `/health`, the request log and `mtplx doctor --explain` count every fallback from the fast path, with the reason. Pi traces include compaction requests and the image context, and the dashboard's draft totals are computed from the per-depth counts when a payload has no flat totals (PR #490, Wu Shuwen).

- **Request captures hold no conversation content by default (PR #356, Philip John Basile).** Capturing is still off unless `MTPLX_REQUEST_CAPTURE_DIR` is set. When it is on, a record holds the settings, token counts and SHA-256 digests, and no prompt text, answer text, messages, exception text or token ids unless each is opted into. For a 200,000-token prompt the default record takes 12 ms and 468 bytes, against 37 ms and 2.0 MB with every token id kept.

- **`mtplx inspect` and `mtplx serve` describe the two new official packs correctly.** They used to say "needs contract repair", ask for the pack to be rebuilt with Forge, and `mtplx inspect` exited with code 3. They now show "Official MTPLX pack, qualification pending" while a pack's exactness measurement is still to be published, the pack runs, and `mtplx inspect` exits with 0. Bonsai 2's measurement is now published, so it shows as verified; Flash-Next Optimized Quality stays pending until it has been loaded on a 256 GB Mac.

- **A pack that needs a newer MTPLX is refused before any weight is read.** When a pack's `min_engine_version` is newer than the running engine, `mtplx serve` and `mtplx inspect` stop with "This model needs MTPLX X or later (you have 2.12.0). Update MTPLX, then try again.", and no unsafe flag overrides it.

- **Quality packs built with Forge carry the Flash-Next sampler settings.** A pack built with the `flash-next-optimized-quality` recipe now records temperature 1.0, top-p 0.95 and top-k 20 in its `mtplx_runtime.json`, as the two Flash-Next Speed packs do. The published Optimized Quality pack's file now carries them as well.

- **A server started without `mtplx serve` uses each model's own sampler.** `python -m mtplx.server.openai` sampled Qwen 3.8, Bonsai 2 and Flash-Next at temperature 0.6 while `/health` reported 1.0. With no sampler flags it now uses 1.0, top-p 0.95 and top-k 20, the settings `mtplx serve` and the app already pass. Explicit flags still win, and Qwen 3.5 and 3.6 stay at 0.6.

- **`mtplx tune` and Forge leave the fans alone unless asked.** Forge's verification runs `mtplx tune`, and tune pinned the fans at maximum even without `--max`, for about a minute during a 9B build. Tune now pins them only with its new `--max` flag or `--require-max-fans`, and Forge passes them only when it is given `--max`. The app's tuning and `mtplx start` still ask for maximum fans. A bare `mtplx tune`, or `mtplx bench tune` without `--max`, now leaves the fans on automatic.

- **Forge keeps a draft head's declared settings unless the evidence is clear.** Calibration switched a grafted Qwen 3.5 9B head to the wrong setting (`pre_norm`) on one prompt and six tokens in which every option accepted nothing. A switch now needs at least 4 prompts, 48 draft rounds per option and a lead of 0.25 accepted tokens per round. Otherwise the declared setting, or the family default, stays, and `mtplx_runtime.json` records the calibration as inconclusive. The probe now samples 8 prompts and 4 windows. On the Qwen 3.5 9B pack it takes 49 s including the model load, and it keeps the pack's setting (1.55 against 1.59 accepted tokens per round, inside the margin).

- **The memory planner never gives a lighter model less context.** On a 16 GB Mac a 7.53 GiB pack planned 12,288 tokens while an 8.08 GiB pack planned 20,480, because only the heavier pack fell through to the tight-machine rule. A lighter pack now drops the cache floor too when that gives it more context, up to what the rule can grant: 24,576 tokens for the 9B layout and 12,288 for the 27B and Bonsai layout. No catalog model's window changes.

- **The `--reasoning-effort` help lists each model's levels and default.** Qwen 3.8 27B offers `xhigh`, `medium` and `low`, and Bonsai 2 offers `xhigh` and `medium`; both default to `medium`. Flash-Next defaults to `xhigh` in chat and to `medium` in coding-agent configurations.

- **`mtplx inspect` reports whether a pack takes images,** and packs that keep their vision tower in one weight file with no index, like Prism ML's, are served with vision.

- **A pack can recommend plain decoding** (`recommended_generation_mode`) and still ship and load its draft head. No shipped pack uses it.

- **If Flash-Next's compiled verifier cannot run on a GPU, the request continues.** Its first dispatch runs under a guard. On a GPU that refuses the kernel, the path is retired with one log line and the same round runs eagerly, and the output is unchanged.

- **Flash-Next's sparse prefill kernel for M1 to M4 checks its numbers before it is used.** The kernel links MLX's private interface, and the app builds it against MLX's macOS 15 release but runs MLX's macOS 26 release, a difference the version check cannot see. Before its first use in a process it now runs one small call on random inputs and compares the result with the pure MLX path, and it is used only when the largest difference is within 0.005. Otherwise Flash-Next prefill runs on the pure MLX path, and `/health` gives the reason.

- **The bundled native kernels load on a fresh Mac.** The app's native wheel now finds its libraries inside the installed package instead of the build machine's paths, and it is built against MLX's macOS 15 release so it loads on macOS 15 and later. A fresh app setup with the bundled Python 3.14.5 and MLX 0.32.2 passed its ABI and GPU checks. The source distribution no longer includes local profiling scripts.

## Known in this release

- Flash-Next Optimized Quality has not been run on a 256 GB Mac yet, and its speed has not been measured. It is listed second on those Macs.

- Bonsai on a 16 GB Mac gets an 8,192-token window. That was measured by limiting a 128 GB Mac to a 16 GB budget, not on a 16 GB Mac. OpenCode's system prompt (about 18,700 tokens) and Hermes's 64K minimum do not fit in that window, so agent clients need 18 GB (20,480 tokens) or 24 GB (94,208 tokens).

- On Flash-Next, compiled and eager verification differ by rounding, for images as for text (see the table above). The sampled-distribution test that 2.11.3 ran for text has not been run for images.

- Long answers still slow down as they go, on Bonsai and on the dense 27B. On a 26,290-token Bonsai answer, speed fell from 50.9 to 30.3 tok/s before the kernels above.
    - Most of that is macOS lowering the GPU clock during sustained decoding: from about 1,450 to about 1,000 MHz on Bonsai, and from about 1,450 to about 670 MHz on the 27B within 150 s, while the GPU stays busy and cools down. The Mac was in High Power mode with the fans at maximum.
    - At a fixed clock, the context itself adds about 0.2 ms per round for every 1,000 tokens, about 5 ms by 24,000 tokens.
    - The kernels make every round cheaper, which is the lever that helps. The rest is the system's clock policy.

- This release was measured on an M5 Max only. M1 to M4, M5 Ultra and macOS 27 were not tested for it, and the macOS 27.2 beta start failure in #504 is not diagnosed yet.

- MLX 0.32.2 for macOS 26 needs macOS 26.2 or later, so MTPLX does not load on macOS 26.0 or 26.1. On those versions the app's setup now says so and asks you to update macOS, instead of pointing to the network.

## Upgrading

`brew upgrade mtplx`, `pip install -U mtplx`, or the app's own update check. You don't need to change any settings. The repetition stop is now off; to turn it back on, set `MTPLX_REPETITION_STOP=1` in the daemon's environment. An existing Flash-Next image conversation is processed again from its first image once, and a long session that an earlier release saved to SSD without the draft head's history is processed once more; nothing is deleted. The Bonsai 2 and Flash-Next Optimized Quality packs require 2.12.0 or later.
