# MTPLX 2.12.0

This release adds Prism ML's Ternary Bonsai 2 27B for smaller Macs and a Flash-Next Optimized-Quality pack for Macs with 256 GB or more. It also brings faster Flash-Next prompt processing and long-context decode, compiled image verification on Flash-Next and the dense 27B, and fixes for reasoning leaks, cancelled starts, stopped conversations and session-cache memory. Each measurement below names the build or test it came from.

*Release draft. Final packaging, public model downloads, image exactness and the complete final-candidate gates are still being verified. The measurements below are saved September 21–22 candidate receipts, not a new measurement of the final 2.12.0 build.*

## Fixes users hit

- **A quoted tool tag no longer ends the thinking.** Pasting a traceback that contained `</parameter>` made the rest of the model's thinking appear in the visible chat, starting at the tag. A thinking block now ends only at `</think>` or at the opener of a real tool call: tools must be declared for the request, the opener must start a line outside a code fence, and a bare `<function=NAME>` must name a declared tool. The same rule decides whether an answer that was only thinking is retried, and a retry that is fed a tool result starts its stream clean instead of carrying the discarded attempt's state. Checked on the release build with the 27B pack: 10 streamed requests (3 without tools, 7 with tools) that quote up to 43 tool tags inside one thinking block, none leaked. The contract has 117 cases in its own test.

- **Gemma 4 streamed replies finish again (#517).** A reply without tools generated normally and then failed with `'Gemma4ThinkingContentStreamSplitter' object has no attribute 'suppressed_tool_markup_chars'`. The stream splitter contract is stated once on the base class and every splitter provides the fields the stream needs. A release-build check streamed 418 frames and finished with `stop`, reasoning separate from the answer. The contract test went from 12 failures out of 37 to 37 passing. The model card's `mtplx bench gemma-mtp` example is stale and will be corrected on the Hub.

- **Stop, then resend, no longer reprocesses the whole prompt.** After Stop the app changed the conversation's server session id, so the resend reached the daemon as a new conversation, found nothing to reuse and processed the full prompt again (26,294 tokens, 24.5 s to the first token in the report). The app keeps the session across a Stop, and the daemon lets a follow-up wait, for at most 30 seconds, while the stopped generation lets go of the session instead of refusing it with a 409. The wait is bounded by `MTPLX_SESSION_CANCEL_HANDOFF_WAIT_S` and the request log records `request_session_cancel_handoff`. The first-token time of the resend after the fix has not been measured on the reporter's conversation.

- **Cancelling an app start no longer aborts the app.** The abort read "freed pointer was not the last allocation" in `swift_task_dealloc`. The daemon supervisor took its health probe and its restart delay as asynchronous closure literals in default arguments of a public initializer; the compiler emits such a closure into every module that calls the initializer under one symbol, the copies can disagree on the size of the asynchronous frame, and the closure then overran its frame into the next task allocation. The defaults are named static functions now. The reproduced debug-build case went from 3 failures in 3 runs to 3 passes, and a start cancelled with Stop no longer writes a failed-start report. For a real failure the app keeps the last 200 lines of daemon output and `mtplx doctor` includes the last 60 when the report is under 14 days old.

- **Long conversations keep what they need to resume (#499).** A 149,649-token prompt with nothing reused and 570 seconds to the first token: when a conversation exceeded its RAM cache allowance, its saved state lost the draft head's history, in RAM and in the SSD copy. That history is kept in both places now. An SSD copy saved by an earlier release without it still needs one fresh pass over the prompt.

- **Old conversation states are counted and released (#456).** Memory grew by 3.7 GiB per turn on a 64 GB M4 Max while the session cache reported zero bytes. The retained state is counted in every session-bank budget, at most one live state is kept per session, and the stale ones are released when superseded or cleared. The 3.7 GiB is the reporter's observation, not a measured saving on the release build.

- **Saving a session to SSD yields to waiting requests (#505).** A request waited more than 500 seconds behind a cache write and then hit its 300-second timeout. Each evaluated and copied unit of the write is at most 32 MiB, with a check for waiting work after each one. A deliberately slowed test interrupts the write in under 200 ms; the reporter's Mac has not been remeasured.

- **A stuck request cannot hold Smart fan control at maximum (PR #295, Patronum).** Fans stayed at maximum for about 15 hours after the client had gone. A request that makes no model progress stops counting as active after 180 seconds, and the existing 120-second idle recovery returns the fans to automatic control. Batched prompt processing reports progress from its own steps, so a healthy long prompt no longer trips the 300-second stream timeout.

- **Tool conversations preserve their prompt history.** With thinking off, an audit of 2,020 conversation turns found the unexplained differences from the model's chat template fall from 848 to 0, and the predicted reusable history matched the next request in 834 of 834 cases, up from 498. For OpenCode conversations with thinking on, a separate reuse check improved from 28 of 36 to 36 of 36. These are prompt-construction checks, not task benchmarks.

- **Seeded plain decoding is consistent (PR #507, David Tai) and imported draft heads accept again (PR #511, Stuart Rowlands).** The optional pipelined plain-decoding path now samples exactly like ordinary plain decoding; a regression test produces the same 12-token sequence at temperature 1.0, top-p 0.95, top-k 20. Qwen 3.5 and 3.8 draft heads imported from outside Forge get the same normalization convention as Forge-built heads; an affected import had accepted about 0 percent of its guesses.

- **Downloaded models can be removed from the app (PR #377, Philip John Basile).** Removal asks for confirmation, targets the exact folder shown, refuses to remove the model being served and says why when it refuses. Additional library folders stay read-only. The controls are translated into all 13 app languages. The CLI honours an explicit model folder when duplicate copies exist.

- **Downloads behind a company proxy explain the certificate failure (#495).** A `CERTIFICATE_VERIFY_FAILED` error names the TLS-inspecting proxy as the cause and lists the fixes; with the optional `truststore` package installed, downloads use the macOS keychain. Forge also accepts a model supplied as a single weights file, which used to stop with `return_hidden requires an MTP-patched runtime`.

- **Request captures contain no conversation content unless asked (PR #356, Philip John Basile).** Capturing stays off by default. A default record holds settings, token counts and fingerprints, never prompt text, answer text, messages or token ids; each of those needs an explicit opt-in. For a 200,000-token prompt the default record costs 12 ms and 468 bytes against 37 ms and 2.0 MB with every token id kept.

- **Eager BF16 verification uses the attention-gate rounding already used by compiled verification.** This affects the shared gated full-attention path in BF16 Qwen3-Next, Qwen 3.5, 3.6 and 3.8 models, including their MoE variants. It applies when verification runs eagerly: dense image requests, contexts beyond the compiled route's 32,768-token limit, buffer-growth fallbacks, warm-restore rounds before compilation, and eager copy, repair or final-save forwards within an otherwise compiled request. The compiled text verify graph, prompt processing and plain decoding keep their existing numerics. Float16 and float32 gates are unchanged, including Bonsai's float16 path. Gemma 4 and Flash-Next use different attention implementations and are unchanged by this fix. Five exact gate tests cover the BF16 contract and the unchanged dtypes and phases.

## Speed

The decode and prompt-processing work from the September 18 to 20 branch is in this release. The headline table above is the whole-request measurement. The component measurements below explain where it comes from; they use different comparisons and must not be added together.

| Measured change | Before | After | What was measured |
|---|---:|---:|---|
| Repeated attention-cache writes at 128K | 7.8 ms | 0.6 ms | The 24 writes alone, M5 Max |
| Attention verification at about 131K | 30.9 ms | 11.2 ms | Twelve attention layers, not the whole model |
| Sampled draft preparation at 4K | about 5.2 ms | about 4.4 ms | September 18 Flash-Next measurement |
| Sparse prompt attention at 64K | 19.8 µs per row | 7.1 µs per row | Component only, Mac in use |
| Selecting prompt-attention blocks at 18K | 2.68 µs per row | 0.58 µs per row | Component only, Mac in use |
| Selecting prompt-attention blocks at 64K | 3.57 µs per row | 2.51 µs per row | Component only, Mac in use |
| Combining intermediate results during prompt processing | 0.22 µs per token | 0.14 µs per token | One operation at width 4,096, Mac in use |
| Memory still allocated between prompt chunks | 88.86 GB | 85.84 GB | Flash-Next, 4,096-token chunks, September 20 |
| Reprocessing near the end of an otherwise reusable prompt | up to 256 tokens | up to 64 tokens | Configured saved-history spacing, not a latency measurement |

- **Long prompts no longer copy their attention memory every step.** Saved attention buffers grow to the size reuse needs and are reused in place. At certain prompt lengths all 24 key and value buffers were copied each verification step, about 135 MB each at 128K; that copy is gone. This is the correction that moved the 128K decode from 46 to 52 tok/s to 63 to 67 tok/s on the development branch, bit-identical output.

- **Speculative guesses wait less.** Flash-Next prepares its sampled guesses together and starts GPU work as each one is ready. The first change measured 88.3 to 92.0 tok/s at 4K and about 2 percent at 16K, with no disagreement across 4,126 grouped steps; the overlap removes host work, but a later pair at equal GPU clocks was flat. The earlier apparent gain coincided with a clock difference, so no separate throughput gain is attributed to the overlap.

- **Prompt processing uses larger chunks where memory and hardware allow.** Flash-Next uses 4,096-token chunks on the supported M5 chips and begins sparse processing at 16K for wide chunks; other hardware keeps its defaults. The final prompt section uses fewer small forwards, finished temporary state is released sooner, and draft-history preparation skips work whose result is discarded. An intermediate change freed 3.0 GB between chunks; the peak figures in the headline table are the release measurement.

- **Less repeated setup.** Attention selection no longer compiles a new GPU program for every new context size, a cost of 40 to 56 ms per new size. Flash-Next prefers the smaller lookup-table files when preparing data and does not reread data already resident in memory.

- **A prompt can no longer take the whole Mac down with it (#516, PR #500 by Maikel Vos).** A 128 GB M5 Max served a long OpenCode session with `allow_swap` on until the kernel's watchdog restarted the Mac with the MTPLX worker at 118 GiB resident; the engine's own guard read below its warning level the whole time because it measured only what the GPU allocator held. Two new readings close that gap. The in-flight guard now reads the process footprint the kernel's own memory manager uses, so memory outside the GPU allocator counts, and it reads the kernel's own figure for the memory it can still hand out (the number behind `memory_pressure -Q`), with an abort floor of 2.5 percent of RAM (3.2 GiB on a 128 GB Mac, never under 1 GiB) and a shed floor at twice that. Under the shed floor the check runs every 2 seconds instead of 10, so the sustained-pressure abort of the running request fires about 6 seconds after the floor is crossed instead of 30. `allow_swap` still admits a prompt past the machine's fit, as the operator asked, but it does not switch this guard off. The reporter's session has not been replayed; the guard is exercised by 27 tests and a rehearsal switch (`MTPLX_SYSTEM_MEMORY_REHEARSAL_AVAILABLE_BYTES`) on a machine that is not short. Kill switch: `MTPLX_SYSTEM_MEMORY_GUARD=0`.

- **Memory protection considers the rest of the Mac before a large prompt (PR #500, Maikel Vos).** Before a large prompt, MTPLX checks what macOS has left as well as its own allocations, frees cached state, and refuses a request that still cannot fit, with the reason. Under sustained critical system pressure the check runs every 2 seconds instead of 10, so the response time falls from about 30 seconds to about 6. The minimum reserve is 2.5 percent of RAM with a 1 GiB floor, 3.2 GiB on a 128 GB Mac. Process accounting includes memory outside the GPU allocator without treating ordinary host memory as an overload.

- **A tight Mac can run a model whose only unfunded need was the warm cache.** The memory planner used to refuse a model when the engine budget could not fund the weights, the 3 GiB runtime transient, the 1 GiB session-bank floor and one 4,096-token block of KV together. The bank floor is a clamp on the warm cache, not a physical need. When only that floor is unfunded, the plan now admits the model with the bank floor at zero, a 256 MiB margin over the transient, and the KV counted at its dense width; restores come from the SSD tier. The rule comes from the Bonsai measurement below, and every plan that funds the bank floor is unchanged to the byte.

- **Performance reports explain more of a slow response (PR #490, Wu Shuwen).** The dashboard, request reports and `mtplx doctor --explain` expose fallback reasons, cache reuse and complete generation-step timing; Pi traces name compaction requests and image context; dashboard draft totals are recovered from per-depth counts when the flat totals are missing.

## Image requests

- **Flash-Next image positions are consistent through the whole reply.** Since 2.10.1 only the main verification forward ran with the image position scope open; the copy-round verification, the repairs and the final save of the reply used plain text positions. After a 1,024-token image the affected rows sat about 990 positions from where they belonged, in RAM and in the SSD copy. One helper now carries the image positions to all eight trunk forward sites. Before the fix a small-model reproduction found 2 of 26 forwards without the scope under the serving default and 25 of 49 with the alternative commit setting; after it, none.

- **Old image history cannot bring the wrong positions back.** Saved Flash-Next image conversations carry a new cache key. After updating, an existing image conversation is processed again from its first image once; text before that image is still reused. Nothing is deleted.

- **Image requests take the compiled verify route on Flash-Next.** Until now an image request fell back to eager verification for the whole conversation. The compiled verifier now owns a rotary origin per request: the image position delta is a graph input of the compiled step, the text trace is unchanged, and two requests with different images share one compiled program. The delta shifts rotary positions only; the cache offset still drives masks, block selection and every cache write. Six prompt shapes that the route cannot represent exactly are refused by name and stay on the eager path, `MTPLX_QWEN4_VISION_COMPILED_VERIFY=0` turns the route off, and `MTPLX_COMPILED_VERIFY=parity2` compares every compiled round against the eager forward. Both routes use the same token-acceptance rule. The saved short image request decoded at 101.6 tok/s compiled and 97.2 eager, with the same 81-token answer and acceptance counts. That is only 22 compiled rounds. The longer instrumented comparison was not bit-identical: text differed in 72 of 105 rounds (maximum recorded KL 0.0069), and the two image requests differed in 53 of 90 and 44 of 88 rounds (maximum 0.0163). A fresh native-sampler image distribution test remains a release gate; matching one short answer does not close it.

- **Qwen 3.5 and 3.8 27B models, and Bonsai, use image-grid positions.** Image rows and the text after them use the position scheme the model expects; the small-tensor reference agreed within 0.000005. Eligible dense 27B image requests use the compiled route described below; Bonsai remains on eager verification in the measured candidate.

- **Dense 27B image requests take the compiled verify route too.** The route carries the image delta as a graph input and leaves the text trace unchanged. Two complete serving runs exercised 18 requests, nine with thinking on and nine with thinking off; every request finished with `stop`, and the instrument compared 762 compiled image rounds and 511 text rounds against the eager verifier from the same cache with zero differences in logits, hidden states, cache state or captures. A seeded 27B image reply run separately on the eager verifier agreed for its first 61 tokens before the two parted, at attention over the eager path's live-length buffers against the compiled path's padded buffers, with identical prefill logits, hidden states, draft inputs and rotary positions: the same rounding class the compiled text lane has always carried, not a position error. `MTPLX_DENSE_VISION_COMPILED_VERIFY=0` keeps dense image requests on the eager verifier; the shared image kill switch `MTPLX_QWEN4_VISION_COMPILED_VERIFY=0` and the state-rebase refusal still take precedence. Flash-Next admission is unchanged.

- **Adding an image reuses the text conversation before it.** A Pi conversation reprocessed 154,899 tokens after an image was attached, 184 seconds. Image requests now take part in the same saved-history restoration as text requests, and the image contents are checked before any image-dependent history is reused. The time on the reported conversation after the fix has not been measured.

## New models

### Ternary Bonsai 2 27B

MTPLX runs Prism ML's Ternary Bonsai 2 27B, a 2-bit ternary model built from Qwen3.8-27B, with image input. The pack `Ternary-Bonsai-2-27B-MTPLX-Optimized-Speed` carries Prism ML's language model and vision tower byte for byte (8.60 GB) and adds the Qwen3.8-27B draft head (0.24 GB), 8.85 GB in total; the served id is `mtplx-bonsai-2-27b-optimized-speed` and the pack requires 2.12.0. The loader applies Prism ML's Hadamard rotation natively and refuses a pack whose rotation metadata or vision tower is missing. Full credit for the model goes to Prism ML; the card carries their license and notice.

The draft head is on by default at depth 1. The September 22 quiet-window run used temperature 1.0, top-p 0.95 and top-k 20, thinking off, 512 generated tokens and one resident model. The table compares Bonsai with its own plain decoder and with the dense 27B candidate on the same Mac.

| Prompt | Bonsai, plain decoding | Bonsai, MTP depth 1 | Dense 27B, MTP | Peak memory, Bonsai / dense 27B |
|---|---:|---:|---:|---:|
| 4,061 tokens | 38.8 tok/s | 50.0 tok/s | 49.8 tok/s | 11.6 / 23.9 GB |
| 16,350 tokens | 34.3 tok/s | 42.6 tok/s | 49.4 tok/s | 14.8 / 27.0 GB |

Bonsai ties the dense 27B at 4K and is slower at 16K in these runs, while using about half the memory. It is a compact-model choice, not a measured speed upgrade over the dense pack. Depths 2 and 3 measured 45.8 and 47.2 tok/s at 4K, below depth 1. The existing exact ternary kernel raised depth 3 to 49.0 tok/s, but it only serves four to eight verify rows and does not accelerate the shipped depth-1 route.

Every Bonsai verify round in the saved 4K run was eager (0 of 293 compiled). A depth-1 round cost 1.98 plain steps, compared with 1.24 predicted by the projection-only measurement; the projection ratio is not a whole-engine timing. Compiled Bonsai verification is a separate experiment and is not claimed as completed here. The earlier laptop-in-use daemon measurements and the benchmark-runner verdict have been superseded by this quiet-window result. Loader parity against Prism ML's runtime was measured on September 18 at mean KL 2.6e-6 in float16; that is a loader comparison, not full sampled-distribution or physical-device qualification.

Memory, measured with the pack loaded under each class's engine budget, text prompts with and without a 1,024-token decode, the draft head and vision weights resident:

| Mac RAM | Engine budget | What the planner admits | Measured peak, prompts up to 8K | Measured peak, 16K prompt |
|---|---:|---|---:|---:|
| 16 GB | 12.0 GiB | 8,192 tokens, no warm cache in RAM | 11.55 to 11.80 GiB | 12.11 GiB (over the budget) |
| 18 GB | 13.5 GiB | 20,480 tokens (36,864 with 8-bit KV) | 11.55 to 11.78 GiB | 12.28 GiB |
| 24 GB | 18.0 GiB | 94,208 tokens (167,936 with 8-bit KV) | 11.55 to 11.78 GiB | 12.28 GiB |

The peak sits 3.06 to 3.08 GiB above the weights plus the KV in every completed run, which is what the planner's transient allowance assumes; 8-bit KV does not lower the peak at these prompt lengths because the KV is held at full width below the paged-cache ceiling. The runs used the Metal memory limit of each class on the 128 GB Mac; a check on a physical 16 GB Mac is still owed, and image requests, the draft head's verification and a populated warm cache are outside this measurement.

### Flash-Next Optimized-Quality

A new Quality recipe for Qwen3.8 Flash-Next: the main model and the draft head at 8 bits with group size 64, the structural weights in BF16, the n-gram lookup table at 4 bits with group size 32 (the fixed-width verifier rejects an 8-bit table). It is intended for Macs with 256 GB or more, where the catalog recommends it first. The recipe is named `flash-next-optimized-quality` in Forge, the streaming audit stamps its own result into the pack, and one command builds, verifies with a full load, and smoke-tests chat, a tool call and an image before writing the card:

```bash
bash scripts/build_flash_next_quality_pack.sh Qwen/Qwen3.8-Flash-Next <output directory>
```

The [170 GB Quality pack](https://huggingface.co/Youssofal/Qwen3.8-Flash-Next-MTPLX-Optimized-Quality) is published with a notice that engine support arrives in MTPLX 2.12.0. Its 57 files passed public size and hash verification. The streaming audit covered all 2,860 tensors and sampled numerical checks across 25 groups. The saved component parity check passed 78 of 78 checks, and the tiny-model build-and-load tests pass. These checks do not establish a full-size model load: the pack retains `full_load_verified: false`, with full-load validation on a 256 GB or larger Mac pending. The automatic n-gram policy streams the table on a 128 GB Mac and keeps it resident from 160 GiB upward, including the 256 and 512 GB tiers; the memory plan counts it when resident. Forge also converts Flash-Next source models directly (PR #508, Bradford Matthews), which used to stop with `Model type qwen4_exp not supported`.

## Catalog and recommendations

The app and the CLI read one catalog of 25 entries with the same identities, sizes and recommendation rule, and model descriptions follow the app language across all 13 languages without a restart. The first recommendation by Mac memory on M3, M4 and M5:

| Mac memory | First recommendation |
|---|---|
| Below 16 GB | Qwen 3.5 4B Optimized Speed (the 4B Quality pack is also listed) |
| 16 to 31 GB | Ternary Bonsai 2 27B Optimized Speed |
| 32 to 255 GB | Qwen 3.8 27B Optimized Speed (Flash-Next when it fits) |
| 256 GB and above | Flash-Next Optimized-Quality |

M1 and M2 keep their FP16 recommendations. Existing selections are preserved.

- **Flash-Next Optimized Speed on a 96 GB Mac** has one 84 GiB engine allowance, a planned 86,016-token window with sparse prompt processing or 20,480 tokens without it; a model classified as too large gets the 4,096-token floor instead of the full 262,144-token maximum by accident.

- **The SSD conversation-cache default follows RAM** from both the app and the CLI: 16 GB on Macs with 16 GB or less, 24 GB up to 32 GB, 32 GB up to 64 GB, 100 GB above that. An explicit limit still wins.

## Control settings for connected apps

- **Use MTPLX settings for connected apps** is a switch in the inference settings that says whether MTPLX or the connected client controls the request settings. It is on by default; turn it off to hand control back to the client, and the native per-chat controls stay available either way. Pi mirrors the live reasoning setting and restores its own choice when the switch is off; its settings synchronization installs separately from user-owned request extensions. A settings read that used to take about 1 second takes 2 to 10 ms without the delayed reused connection. The switch is translated into all 13 app languages.

### Exactness measurements

The dense per-round comparison and the Flash-Next numerical comparison answer different questions. Dense rounds were replayed from the same cache state; that does not make two independently sampled full replies bit-identical. Flash-Next also differs numerically between compiled and eager **text** verification, so the image result cannot be described as an image-only defect or as proven harmless by analogy. The final gate must retain logits, live cache rows, rotary positions, restore into generated tokens and the native-sampler distribution comparison. No fresh image-distribution result is claimed in this draft.

## Known in this release

- Final fixed-commit regression coverage is still open: Flash-Next 128K, sustained output, real-client task time, dense compiled-versus-eager image timing and the roughly 2 percent dense verify-round slowdown recorded consistently in both earlier pairs. The last item needs a targeted comparison of `e36f5ffb`; being below a hard-stop threshold does not prove it is noise.

- The Quality pack is published and its 169.96 GB download is hash-verified. The 166.2 GiB memory estimate remains a planning figure; full-load validation needs a 256 GB or larger Mac. The app's download gate asks for approximately 395.7 GiB free on the model-store volume; CLI model selection does not apply that disk gate.

- Bonsai's 16 GB tier was measured by restricting a 128 GB Mac's engine budget. Image requests, populated warm-cache pressure and a physical 16 GB Mac need separate evidence. M1 and M2 retain the existing FP16 recommendation ladder; the Bonsai-first recommendation currently applies to M3 and newer.

- Native app Stop followed immediately by resend, connected-app setting ownership, Pi compaction with image history and the time from the last token to the final event remain explicit final-package QA cases.

- The optional setting that raises GPU submission limits and the optional restore points inside a larger prompt forward stay off by default. New prefill and Bonsai experiments are not included in these measurements unless their final results are added here.

## Upgrading

```bash
pip install --upgrade mtplx
```

After publication, update the app from its Check for Updates menu, use `brew upgrade mtplx`, or run the pip command above. Existing Flash-Next image conversations are processed again from their first image once after the update; nothing else in the session store changes. The Bonsai pack requires 2.12.0 or newer.
